# 协议笔记（蓝牙 / Wi-Fi PTP/IP / USB）

本文记录 App 实现所依据的协议细节及其出处。出处分为两类：
- **libfuji `lib/*.c` @ `90aaa93`**：本仓库。
- **furble @ `0cac22a`**：只做对照。

这里的内容**都没有在 X-T30 III 上验证过**。需要真机确认的项目在文中标为 ⚠️，并列入 [X-T30-III-VERIFICATION.md](X-T30-III-VERIFICATION.md)。

## 总体分工

| 链路 | 用途 | 不用于 |
|---|---|---|
| 蓝牙 LE | 发现、配对、登记客户端名称；请求相机开启 Wi-Fi；遥控快门；时间/位置同步；读取型号、固件版本 | **传输照片**。照片一律走 Wi-Fi |
| Wi-Fi（相机热点，PTP/IP） | 图库、缩略图、下载、实时取景、属性读写 | — |
| USB（ImageCaptureCore） | 相机设为“USB 读卡器”时导入文件；只读的 PTP 诊断 | 联机拍摄、RAW 转换、备份/恢复（本版入口关闭） |

界面上，蓝牙、Wi-Fi、会话三种状态**分别显示**。只有 PTP 会话建立成功，才算“已连接相机”。

## 蓝牙 LE

UUID 常量见 `FujiKit/Bluetooth/FujiBLEProtocol.swift`。下表给出 UUID 前缀，完整值在代码中。

### 广播识别

- 制造商数据的公司 ID 为 `0x04D8`（字节 `d8 04`），对应 libfuji.json 的 `bluetoothFilters`。
- **旧版、处于配对模式**：数据长 7 字节，第 3 字节为 `0x02`，后 4 字节是**配对令牌**。
- **安全方案**：数据长 8 字节，后 5 字节是序列号。
  - 处于配对模式时广播服务 `A9D2B304…`。
  - 已绑定、等待重连时广播 `123D8F06…`。
- 其他长度标为“无法识别”，不提供配对。⚠️ X-T30 III 的实际格式待确认。

### 配对方案的判定（不混用）

连接后先做服务发现：
- 只有 `91F1DE68…`：**旧版令牌**。
- 只有 `123D8F06…`：**安全绑定**。
- 两者都有：依次用保存的方案、广播提示，最后默认旧版。
- 两者都没有：报错。

已保存的方案与相机当前方案不一致时，报告“配对方式不一致”，**不会自动切换**，需要用户重新配对。

**旧版流程**（libfuji `bluetooth.c`、furble FujifilmBasic）：
1. 向 `91F1DE68…/ABA356EB…` 写入 4 字节令牌。令牌来自配对模式广播；重连时用钥匙串里保存的令牌。
2. 向 `91F1DE68…/85B9163E…` 写入客户端名称：可打印 ASCII，最多 26 个字符。
3. 订阅以下特征：
   - 必需：IND1 `A68E3F66…`、IND2 `BD17BA04…`、NOT1 `F9150137…`、地理标记更新 `AD06C7B7…`、IND3 `049EC406…`。
   - 可选：SSID 特征。

**安全流程**（furble FujifilmSecure、libfuji 安全分支）：
1. 读取 `123D8F06…/F557D96B…`（4 字节状态）。该特征需要加密，读取会触发 **iOS 系统配对对话框**。
   - iOS 没有 createBond API，只能通过读取加密特征来触发。
   - 等待时间放宽到 90 秒，让用户在相机和 iPhone 上确认。
2. 把状态的第 4 字节（下标 3）改为 `0x20` 后写回。
3. 向 `85B9163E…` 写入客户端名称。
4. 按 furble 的顺序订阅：
   - 必需项订阅失败时中止。
   - 可选项失败只记录，并在界面上显示“N 项可选通知未订阅”。
5. 向 `C95D91AE…` 写入地理标记同步间隔 10 秒（u16 LE）。

**失效与错误**：
- `CBError.peerRemovedPairingInformation`：相机端已删除配对。App 会提示用户到“系统设置 → 蓝牙”忽略该设备后再配对。
- 令牌写入被拒：提示检查相机是否处在配对登记界面，以及“选择配对目标”设置。
- 断开时附带的错误信息会显示在“蓝牙”状态行。

**标识**：保存的是 `CBPeripheral.identifier`（每台 iPhone 不同的 UUID），不读取也不保存 MAC 地址。令牌和序列号存入钥匙串。

### 请求相机开启 Wi-Fi（libfuji `fuji_bluetooth_connect_to_wifi`）

1. 读取 SSID 特征 `BF6DC9CF…`（UTF-8，以 NUL 填充）。
2. 先开始等待 IND1，再向 `600655E6…`（快门服务中的第二个特征）写入 `04 00`。
3. 读取密码特征 `E809256A…`。读到后立即注册给日志脱敏器，并存入钥匙串。
4. 查看 IND1 第 1 字节：`01` 表示就绪，`00` 表示忙，此时报“相机忙”。

⚠️ libfuji 注释里说，XApp 和旧版协议的判定“尚不确定”。

### 遥控快门（`7FCF49C6…`）

每个动作写两次：先写命令 `01 00`，再写参数：
- 对焦：`03 00`
- 按下：`02 00`
- 释放：`00 00`

App 提供两种按钮：“半按对焦”第一次点击发送对焦，再点一次发送释放；“按住拍摄”在手指按下时发送按下，松开时发送释放。

**间隔拍摄**：由 App 计时，**只在前台运行**。App 离开前台（scenePhase 不再是 active）就停止，不用任何手段保持后台运行。

### 时间与位置

- **时间**：NOT1 发来通知时，向 `B9BFD37F…` 写入 7 字节：u16 年（LE），然后月、日、时、分、秒各 1 字节，用本地时区。可在“遥控”页关闭“连接后自动同步时间”。
- **位置**：只在用户开启“向相机提供位置”后才申请“使用期间”定位权限。
  - 相机通过地理标记更新特征发送 `01 00` 请求位置。
  - App 回写 23 字节到 `0F36EC14…`：i32 纬度 ×1e7、i32 经度 ×1e7、i32 海拔（米）、4 字节填充，加上 UTC 时间（7 字节）。
  - 没有有效定位时**不发送**。libfuji 中的 `update_geo_data()` 写的是测试用的固定坐标，App 不沿用。

### 设备信息

从标准 Device Information 服务（`180A`）读取型号 `2A24`、制造商 `2A29`、固件 `2A26`、软件版本 `2A28`。镜头名和镜头固件只在相机提供相应特征时显示。

## Wi-Fi 加入与真实连接确认

1. 用 `NEHotspotConfiguration(ssid:passphrase:isWEP:false)` 加入网络。
   - 设置 `joinOnce = false`。系统文档说明 joinOnce 网络在后台 15 秒后会被断开，那样会中断传输。
   - 先按隐藏网络尝试（libfuji/fudge 在密码来自蓝牙时这样设置），失败后再按普通网络尝试。
2. `apply` 成功**只说明配置已被接受，不代表已经连上**。之后要：
   - 确认存在通往 `192.168.0.1` 的本地接口路由；
   - 对 `192.168.0.1:55740` 做 TCP 探测。
   两项都通过后，状态才变为“已连接”。
3. 以下情况会进入**手动加入**页面：系统拒绝自动加入（例如 NoHotspot 构建没有该权限）；App 不在前台；用户拒绝加入请求（此时用的是已保存在钥匙串里的网络名称和密码）；或者加入后仍连不上相机。页面上显示网络名称，可拷贝名称和密码，用户在系统设置里加入后回到 App，App 再做第 2 步的确认。
4. PTP socket 通过 `IP_BOUND_IF` 绑定到相机所在接口，避免 iOS 判断该 Wi-Fi 没有互联网后改走蜂窝网络。

## PTP/IP 会话（libfuji `fuji_setup`）

- **地址与端口**：
  - 相机 `192.168.0.1`。
  - 命令端口 `55740`，事件端口 `55741`，实时取景端口 `55742`。
- **数据包格式**：在 TCP 上使用 USB 风格的容器（`PTP_IP_USB`），初始化包是富士的自定义格式。
- **握手**：`ptpip_fuji_connect_handshake` 发送客户端名称，最多重试 2 次。相机会显示连接请求，⚠️ 可能需要用户在相机上按 OK。
- **OpenSession**：握手后等 50 ms 再发 OpenSession。富士要求 OpenSession 的**事务 ID 从 1 开始**，而不是 PTP 标准的 0。
- **事件与状态**：
  - 事件列表在属性 `D212` 中，相机状态在 `DF00` 中：
    - `0`：等待访问（需要用户在相机上确认）。
    - `1`：多张传输（在相机上选了图片）。
    - `2`：完全访问。
    - `3`：PC AutoSave。
    - `6`：远程访问。
  - 处于“等待访问”时，libfuji 每 100 ms 轮询一次。App 给整个 setup 加了 120 秒看门狗，用户也可以取消（libpict 补丁提供的 `shutdown()` 会打断阻塞的读取）。
- **版本协商**：`DF21`/`DF22`/`DF24`/`DF25`/`DF28`。按 libfuji 逻辑读取，必要时回写。用 `DF01` 设置客户端状态（模式）。
- **传输模式（transport）**：
  - `2`：在相机菜单中发起的无线通信。
  - `9`：XApp 模式，即由蓝牙引导的 Wi-Fi。相机报告 `remote_version < 0x20007` 时，libfuji 降级为 `2`。
  - ⚠️ X-T30 III 实际进入哪种模式，以会话日志中的 `transport=` 为准。
- **会话建立后**：App 每秒轮询一次事件，获取对象数量变化、相机推送的文件，以及断线情况。

### 图库与下载

- **对象句柄**：`GetObjectHandles` 返回 `1…N`。**句柄只是当前列表中的序号，不能当作身份**。App 用“文件名 + 大小 + 拍摄时间”作为对象身份。每次下载或续传前，都按身份重新找到句柄。
- **缩略图**：`GetThumb`，结果缓存在本地。
- **下载流程**（与 `fuji_download_file_ex` 相同）：
  - transport 2：先 `fuji_get_events`，再设 `D227 = 1`（EnableCorrectFileSize），然后读 ObjectInfo，用 `GetPartialObject` 按每块 1 MB（`0x100000`）读取，最后把 `D227` 复位为 0。
  - transport 9：设 `D226`，`1` 表示让相机缩小图片，`2` 表示原图；下载后复位为 2。
  - ⚠️ D226 的确切含义（缩小到多大，是否影响 RAF/视频）需要真机确认。
  - App 默认**不缩小**。缩小后得到的文件单独标记为“相机缩小版”，与原图、缩略图三者区分。
  - 开启“记录下载前后的相机属性”后，下载前后各读一次 D226/D227 写入日志，用来核对开关是否真的生效。
- **续传**：
  1. 按身份找到句柄后，读取续传点之前 64 KB 的数据，与本地临时文件比对。
  2. 一致才从该偏移继续下载，否则从头开始。
  3. 文件完成后检查长度和格式完整性：JPEG 以 EOI 结尾、RAF 头部正确、HEIF/MOV/MP4 的 box 结构完整。
  4. 最后计算 SHA-256 去重。
- **事务顺序**：每个会话的所有 C 调用都在同一条工作线程上逐个执行，PTP 事务不会交错。任务按优先级排队：用户操作优先于缩略图预取，同一优先级内先进先出。一个文件的下载是一个完整任务，下载期间的其他请求会排在该文件之后；取消通过 `fujiios_request_cancel` 在分块之间生效。

### 实时取景

用 `fuji_config_liveview` 开启后，从 `55742` 读取帧：每帧有 18 字节头，后面是 JPEG。帧读取已经过补丁 0005 加固。关闭时调用 `fuji_end_liveview`。⚠️ X-T30 III 是否允许在 transport 9 下开启实时取景，待验证。

### 属性

- 读取属性描述符（GetDevicePropDesc）的原始字节，由 Swift 做带边界检查的解析。
- **只有可写、而且相机列出了允许值（枚举，或可展开的范围）的属性**才提供修改。修改前展示属性码、当前值和目标值，并请用户确认；写入后重新读取核对。
- 电量只显示相机给出的档位，例如“档位 2/3”，**不换算成百分比**。

## USB（ImageCaptureCore）

- 用 `ICDeviceBrowser` 发现相机，用 `ICCameraDevice` 读取文件目录并下载文件，下载结果走同一个传输引擎（身份、完整性、去重、存入照片）。
- “PTP 只读诊断”通过 `requestSendPTPCommand` 只发送 `GetDeviceInfo`（0x1001）和 `GetDevicePropValue(0xD16E)`（USB 模式，libfuji：5 联机拍摄、6 RAW 转换/备份恢复、8 网络摄像头），**不发送任何写入命令**。
- iOS 不允许第三方 App 直接占用 USB 端点，因此 libpict 的 libusb 后端只做了桩函数；也没有使用 ExternalAccessory。
